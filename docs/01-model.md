# 01. 시뮬레이션 모델

모든 계수는 `packages/data/seed/config.json` 과 각 모듈 상단의 상수에 있다.
숫자를 바꾸면 `npm run sim -- auto` 로 즉시 영향을 확인할 수 있다.

## 1. 시간

분기(quarter) 단위 턴. **2020Q1 ~ 2026Q4 = 28턴**.

한 턴의 처리 순서는 `packages/engine/src/reduce.ts` 의 `advanceTurn()` 이 전부다.

```
1) 조직·투자·인수 결정 반영        (일회성 지출 발생)
2) 입찰 판정                       (이번 분기 공고 대상)
3) 기존 사업 수행                  (매출 인식, 품질, 실적 축적)
4) 수주분을 다음 분기 수행 대상으로 편입
5) 제품 반복매출 / 인수 승계매출
6) 인재 ramp 진행 및 이탈 판정
7) 재무 정산 및 파산 판정
8) 사기·기술부채·자격취득 드리프트, 분기 진행
```

이 순서에 의미가 있다. **수주한 사업은 다음 분기부터 수행**되므로 계약과 현금 사이에
시차가 생기고, 성장 전략은 거의 항상 현금 문제로 나타난다.

## 2. 회사 상태

`CompanyState` (`types.ts`). 주요 항목만 옮기면:

| 항목 | 의미 |
|---|---|
| `cashKRW` / `debtKRW` | 현금과 차입. 게임의 진짜 제약 |
| `staff` | 등급별 인원 (특급/고급/중급/초급) |
| `capability` | 도메인 역량 0~100 (ai, data, si, edu, cloud) |
| `channel` | 세그먼트 영업력 0~100 (public, enterprise, global, smb) |
| `certs` / `vendorRegistrations` | 자격·인증과 벤더 등록. 입찰의 관문 |
| `trackRecords` | 완료 사업 실적. 플라이휠의 연료 |
| `relations` | 발주기관별 관계자본 0~100 |
| `morale` / `techDebt` / `brand` | 조직 상태 |

## 3. 적합도(fit) — 모델의 심장

`fit.ts`. 실제 공공 제안 평가표 구조를 그대로 본떴다.

### 3.1 게이트 (통과 못 하면 입찰 자체가 불가)

```
필수 자격(mandatoryCerts) 미보유  →  입찰 불가, 단 컨소시엄으로 보완 가능
벤더 등록(vendorRegistration) 미보유 →  입찰 불가, 컨소시엄으로도 보완 불가
```

**벤더 등록을 컨소시엄으로 못 메우게 한 것이 의도적인 설계다.** 대기업·글로벌
세그먼트는 인재 영입이나 M&A 로만 열린다 — 그게 이 게임에서 사람과 회사를 사는 이유다.

컨소시엄을 쓰면 자격은 빌리지만 계약금액의 **30%(`CONSORTIUM_SHARE`)** 를 파트너에게 넘긴다.

### 3.2 항목별 점수 (각 0~1, 실적만 최대 1.2)

| 항목 | 계산 |
|---|---|
| 실적 | `clamp(보유 유사실적 / 요구실적, 0, 1.2) × (0.7 + 0.3 × 평균품질)` |
| 인력 | 여유 인력으로 요구 투입인력을 채운 비율. 상위 등급이 하위 자리를 대신할 수 있다 |
| 기술능력 | 사업 도메인의 역량 평균 / 100 + 보유 제품의 기술 가점 |
| 관리방법 | `0.45 + 브랜드/250 + 사기/400 − 기술부채/200` |
| 상생 | 컨소시엄 0.9 / 단독 0.5, + 브랜드/500 |

같은 발주기관에 같은 도메인 실적이 있으면 **기존 수행사 프리미엄**(`incumbentAdvantage`)이
실적 점수에 가산된다.

### 3.3 최종 점수

```
techScore     = Σ (배점_i × 점수_i)                      → 0~100
relationBonus = 관계자본/100 × 세그먼트가중 + 채널/100 × 세그먼트가중
fitScore      = clamp(techScore + relationBonus + 영입가점 × 100, 0, 100)
```

세그먼트별 관계자본 가중치는 `public 12 / enterprise 15 / global 7 / smb 6`.
대기업이 공공보다 관계가 더 크게 작동하도록 잡았다.

## 4. 입찰 판정

`bidding.ts`.

```
priceScore = 100 × (할인율 / 최대할인율)^0.7
myTotal    = (fitScore × 기술배점 + priceScore × 가격배점) / 100

경쟁사 i:  tech  ~ N(55 + 경쟁강도 × 33,  9)
           price ~ N(45 + 경쟁강도 × 35, 14)
           total = (tech × 기술배점 + price × 가격배점) / 100

승리 = myTotal > max(경쟁사 total)
```

경쟁사 점수는 시드 PRNG 로 샘플링하므로 같은 시드에서는 항상 같은 결과가 나온다.
`55 + 강도 × 33` 이 **난이도 손잡이**다 — 낮추면 거의 다 이겨서 현금 압박이 사라진다.

패배해도 제안 비용(예산의 `proposalCostRate`)은 매몰된다. 자격 미달로 게이트에서
막히면 제안서를 쓰지 못하므로 비용도 발생하지 않는다.

## 5. 수행과 플라이휠

`delivery.ts`. 이 모듈이 게임의 순환을 만든다.

### 분기 품질

```
가동률 초과 페널티 = max(0, 가동률 − 0.85)² × 1.6      ← 비선형. 넘는 순간 급격히 나빠진다
품질 = 0.35 + 도메인역량 × 0.45 + 사기/500 + 보정
       − 기술부채/300 − 초과페널티 − 통합중 페널티 + N(0, 0.05)
```

### 완료 시 되돌아오는 것

- **실적 축적** — 도메인마다 `TrackRecord` 1건. 다음 입찰의 실적 배점을 직접 끌어올린다
- **관계자본** — `(평균품질 − 0.55) × 30`. 잘하면 오르고 못하면 **떨어진다**
- **역량 학습** — `평균품질 × 2.5 × 사업규모계수`
- **브랜드** — `(평균품질 − 0.5) × 3 × 사업규모계수`

품질 0.5 미만인 분기는 기술부채로 남는다. 이것이 역방향 플라이휠이다:
과다 수주 → 품질 저하 → 관계자본 하락 + 기술부채 → 다음 입찰 불리.

## 6. 인재

`talent.ts`. 두 가지가 핵심이다.

- **`rampQuarters`** — 효과가 100% 발현되기까지 걸리는 분기 수. 상태에는 절대값만
  저장하므로 매 분기 "이번에 새로 발현된 만큼"의 증분만 더한다
- **`attritionRisk`** — 이탈 확률. 조직 사기가 낮으면 커진다

```
이탈확률 = attritionRisk × (1 + max(0, 60 − 사기)/60 × 문화민감도 × 2.5)
```

이탈하면 그때까지 발현된 효과를 **전부 되돌린다**. 단 벤더 등록은 한 번 열리면
유지된다 (등록은 법인 단위이므로).

## 7. M&A

`mna.ts`. 인수의 값어치와 위험을 함께 모델링한다.

### 즉시 넘어오는 것
- 인력 (이탈률 `attrition` 만큼 빠져서)
- 역량·채널 — **합이 아니라 `max(A, B) + min(A, B) × 0.15`**.
  이미 잘하는 영역을 사면 거의 값이 없고, 없는 걸 사야 값이 있다는 뜻
- 벤더 등록, 관계자본, 제품

### 통합이 끝나야 넘어오는 것
- **조달 실적과 인증**. 법인 통합 절차가 끝나야 우리 이름으로 쓸 수 있다.
  인수의 진짜 값어치는 통합에 성공해야만 손에 들어온다

### PMI (통합 후 관리)
```
통합 기간 동안        : 승계 매출 70%만 인식, 수행 품질 −0.08
통합 종료 시점        : 실패 확률 = (1 − 문화적합도) × 0.5
  실패 시            : 인력 40% 추가 이탈, 승계매출 55%로 감소, 실적 절반만 승계, 사기 −12
통합 완료 후          : 승계 매출이 분기마다 12%씩 감소 (계약 만료·고객 이탈)
                       교차판매 시작 (분기당 고객의 12% 전환)
```

**승계 매출이 감소하는 것이 중요하다.** 이게 없으면 인수가 리스크 없는 연금이 되어
지배 전략이 된다. 매출을 유지하려면 결국 그 채널에서 새 사업을 따야 한다.

### 차입 한도
```
한도 = max(10억, 직전 4분기 매출 × 1.5)
```
매출이 없는 회사는 큰 회사를 살 수 없다. 먼저 사업으로 규모를 키워야 레버리지를 쓸 수 있다.

## 8. 재무

`finance.ts`.

```
매출  = 사업 매출 + 제품 반복매출 + 인수 승계매출
비용  = 인건비 + 간접비(고정 + 인건비 × 0.22) + 직접원가(사업매출 × 0.08)
        + 이자(차입 × 2.2%) + 일회성 지출
현금  = 현금 + 손익 − 원금상환(차입 × 6%)
```

**원금 상환이 손익에는 안 잡히지만 현금은 빠져나간다.** 이자만 내는 모델에서는
레버리지 인수가 거의 공짜가 되므로, 원금을 갚게 해야 "인수는 몇 년간 현금을 묶는다"는
실제 부담이 생긴다.

파산은 현금이 `bankruptcyCashKRW`(−10억) 미만인 상태가 **3분기 연속**일 때.
한 분기 적자로는 망하지 않는다.

## 9. 밸런싱 현황

`npm run sim -- auto --strategy all --runs 200` 로 자동 판정한다.
2026-08 기준 `ontact` 프로필 실측:

| 전략 | 누적매출(중앙) | 최종현금 | 파산율 | 목표달성 |
|---|---:|---:|---:|---:|
| 공공 집중 | 680억 | 111억 | 0% | 78% |
| M&A 우선 | 845억 | 73억 | 4% | 77% |
| 제품 R&D | 340억 | 18억 | 3% | 19% |
| 균형 | 301억 | 15억 | 4% | 13% |
| 대기업 집중 | 299억 | 8억 | 16% | 57% |

판정 기준 4/5 통과. **미충족 1건**: 최고-최저 전략 격차가 2.75배로 목표(2.5배)를
약간 넘는다. 원인은 `균형`·`대기업 집중` 프리셋이 여러 세그먼트에 자원을 분산해
어느 쪽에서도 임계 규모에 못 미치는 것이며, 모델 결함이라기보다 봇 전략의 한계다.
사람이 플레이하면 상황에 맞춰 집중할 수 있으므로 이 격차는 더 줄어든다.
